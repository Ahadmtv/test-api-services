# ADR 0005: API نسخه‌دار، خطا و کنترل دسترسی

- وضعیت: پذیرفته‌شده برای طراحی MVP

## زمینه

API به قرارداد قابل آزمون میان مشتری، ارائه‌دهنده، مدیر و backend نیاز دارد. عملیات مالی تکرارشونده و داده نقش‌ها/رزروها حساس‌اند.

## تصمیم

API با prefix `/api/v1` و قرارداد OpenAPI 3.1 مرجع تعریف می‌شود؛ توضیحات توسعه‌دهنده و endpointها فارسی‌اند. زمان‌ها RFC 3339 با UTC/offset و مبلغ دامنه integer IRR است. فهرست‌ها cursor-based هستند. عملیات تغییردهنده مالی و رزرو کلید idempotency دارند؛ بازاستفاده همان کلید با محتوای متفاوت conflict است.

خطاها `application/problem+json` با `code` پایدار، عنوان فارسی و `request_id` هستند. خطای خام پایگاه داده، stack trace، راز و پاسخ خام provider به مصرف‌کننده نمایش داده نمی‌شود. middleware احراز هویت principal معتبر می‌سازد، اما دامنه نقش و مالکیت resource را هم کنترل می‌کند؛ شناسه/نقش ارسالی کاربر مرجع اعتماد نیست. audit برای عملیات مالی و مدیریتی لازم است و داده‌اش حداقلی است. روش auth/OTP و provider پیامک هنوز انتخاب نشده است؛ تصمیم آن باید پیش از مرحله هویت ثبت شود.

### مدیریت و امنیت فایل‌های تصویری

- **فرمت‌های مجاز و استانداردسازی:** سامانه‌ی آپلود تصاویر نمایه و کاور تنها فایل‌های با فرمت JPEG، PNG و WebP را می‌پذیرد. نوع واقعی فایل بر اساس محتوا (magic bytes) و رمزگشایی تصویر شناسایی می‌شود و صرفاً به Content-Type کلاینت اعتماد نمی‌شود. تصویر پس از اعتبارسنجی مجدداً به‌صورت یک فایل JPEG تازه با کیفیت ۸۵ و با ابعاد نرمال‌شده (نسبت ۱:۱ برای نمایه و ۱۶:۹ برای کاور) کدگذاری می‌شود؛ کلیه متاداده‌های حساس ورودی نظیر داده‌های مکانی EXIF/GPS به‌طور خودکار پالایش و دور ریخته می‌شوند و جهت‌گیری تصویر (EXIF Orientation) پیش از برش اعمال می‌گردد.
- **محدودیت‌های اندازه و پیشگیری از DoS:** حداکثر حجم فایل ورودی ۵ مگابایت است که توسط Guard اختصاصی و بررسی استریم کنترل می‌شود. پیش از بازکردن کامل تصویر در حافظه، ابعاد تصویر توسط `image.DecodeConfig` استخراج و در برابر سقف مجاز (حداکثر ۸۰۰۰ پیکسل و ۴۰ میلیون پیکسل کل) ارزیابی می‌شود تا از حملات بمب حافظه (Pixel Flood / Decompression Bomb) جلوگیری شود. پردازش تصویر نیز توسط سمافور هم‌زمانی به تعداد هسته‌های پردازنده محدود شده است. همچنین حداقل ابعاد برای نمایه ۱۲۸ پیکسل و برای کاور ۳۶۰ پیکسل تعیین شده است.
- **راهبرد ذخیره‌سازی امن:** فایل‌ها درون مسیر `static/img` ذخیره می‌شوند. نام فایل‌ها منحصراً از UUIDv4 تصادفی تولیدشده در سرور مشتق می‌شود و هیچ نام یا مسیر ارسالی از کلاینت در نام‌گذاری دخالت ندارد. نام کلیدها با الگوی مشخص Regex بررسی می‌شوند تا از هرگونه دستکاری مسیر و Path Traversal ممانعت به عمل آید. ایجاد فایل به‌صورت اتمیک ابتدا در فایل موقت انجام شده و سپس با Rename نهایی می‌شود. سرویس‌دهی استاتیک با هدر امنیتی `X-Content-Type-Options: nosniff` همراه است.
- **کنترل دسترسی و مالکیت:** مسیرهای `/api/v1/me/images/*` مستلزم توکن احراز هویت معتبر هستند و هر کاربر فقط امکان ثبت، جایگزینی یا حذف تصاویر متعلق به حساب خود را دارد. بارگذاری و حذف تصویر کاور اختصاصاً مشروط به داشتن نقش `provider` است.
- **سازگاری داده‌ها و چرخه عمر:** عملیات جایگزینی تصویر در سطح پایگاه داده با قفل `FOR UPDATE` انجام می‌گیرد و پس از ثبت رکورد جدید، فایل قدیمی حذف می‌شود. در صورت شکست ثبت متاداده، فایل جدید ذخیره‌شده پاک‌سازی می‌شود تا فایل هرز در دیسک باقی نماند. حذف تصویر کد 204 No Content، ایجاد تصویر جدید کد 201 Created به همراه هدر Location، و جایگزینی تصویر کد 200 OK بازمی‌گردانند. هرگونه تغییر تصویر منجر به ثبت رخداد حسابرسی (`user.image.updated` یا `user.image.deleted`) می‌گردد.

## پیامدها

- تغییر API با OpenAPI، آزمون قراردادی و نسخه‌گذاری هماهنگ می‌شود.
- رفتار خطا و مجوز پایدار و قابل آزمون است؛ کاربران جزئیات داخلی را نمی‌بینند.
- احراز هویت، rate limiting، مدیریت امن راز، TLS، حداقل‌سازی PII و بازبینی حقوقی/حریم خصوصی شرط آماده‌سازی تولید هستند.
- سامانه تصویر از مخاطرات امنیتی معمول (آپلود بدافزار، خواندن فایل‌های دلخواه، فرسایش منابع و نشت اطلاعات مکانی) محافظت شده است.
